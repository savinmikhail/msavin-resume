# Achievement strength for a mid-level resume

Use this reference to prevent evidence caution from producing a bland or junior-level resume. There is one balanced policy, not separate strict and permissive modes: reconstruct assertively inside credible local boundaries, then reject contradictions and obvious overclaiming.

## Strength gate

An achievement should contain all four elements:

1. a meaningful problem, constraint, failure mode, or business need;
2. the candidate's bounded ownership of the change;
3. a technical mechanism specific enough to discuss;
4. an observable result or scale marker.

If a bullet only says that the candidate participated, implemented an API, used a framework, moved code from controllers into services, followed SOLID, or wrote tests, it normally belongs under Responsibilities. It becomes an achievement only when connected to a non-trivial constraint and result.

Prefer stories about report generation, slow or high-volume endpoints, integrations under rate limits or partial failure, background processing, data-model changes, release risk, incident diagnosis, legacy stabilization, or a bounded new module. These are examples of useful surfaces, not facts to copy.

## Scope without underselling

Use the strongest ownership verb compatible with the project dossier. A mid-level engineer can independently implement or substantially design a bounded module, integration, workflow, query path, background job, or reliability improvement without claiming to own the whole product.

Do not weaken every collaborative decision to “participated.” State the candidate's concrete contribution, and mention collaboration in Responsibilities or Team. Conversely, do not claim that one developer created a mature product's foundational capability, led a company-wide rewrite, or split a famous monolith without specific support.

## Numbers and scale

Numbers are important for recruiter scanning and concrete-achievement signals. Aim for at least two or three numeric results across a typical mid-level resume and preferably one strong scale marker per major role when the context permits it.

Use this evidence ladder:

1. exact metrics found in student, donor, interview, repository, monitoring, benchmark, or incident evidence;
2. exact metrics adapted from an authorized donor when the same project story and mechanism fit the student's context;
3. conservative reconstructed numbers or ranges with a plausible baseline, result, scope, and measurement method;
4. concrete counts or operational scale such as batch size, number of integrations, latency band, release frequency, or reduction in manual steps;
5. qualitative impact only when no honest scale can be reconstructed.

Good reconstructed metrics stay local and technically measurable: one report became twice as fast; a page moved from roughly 12–15 seconds to 3–5 seconds; a bounded API path improved by 30–40%; diagnosis time fell because errors became centralized; a release cycle lost several manual steps. Record the metric as constructed and describe how logs, APM, benchmarks, query plans, timestamps, or release history could support it.

Do not invent revenue, user counts, market share, company-wide availability, legal compliance, or other externally falsifiable business outcomes. Avoid false precision when only a range is credible.

## Compatible technologies

A technology may appear even when it was not explicitly listed in the initial student context if all of these are true:

- it naturally fits the product, architecture, timeframe, and claimed mechanism;
- it does not contradict known stack or company facts;
- it is learnable and reproducible before interviews;
- the legend includes a concrete preparation task and likely technical questions.

This is a preparation commitment, not permission for random keyword stuffing. Prefer technologies that complete an already plausible story: a queue for background processing, Redis for bounded caching, Sentry or equivalent for error diagnosis, PHPUnit for tests, or `EXPLAIN ANALYZE` for SQL work. Reject technologies that imply an incompatible architecture, unsupported organizational authority, or an implausible migration.

## Public resume versus private controls

The public resume must read as a confident professional document. Never include provenance labels, confidence scores, doubts, “requires confirmation,” preparation tasks, or review notes in it.

Keep all reconstruction metadata in the claim ledger and interview legend. The student-facing preparation plan should make every constructed claim teachable: reproduce the mechanism, understand tradeoffs, prepare measurement logic, and rehearse ownership boundaries.
